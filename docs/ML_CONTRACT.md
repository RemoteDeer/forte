# Контракт локального ML-адаптера

## Текущий пакет: forte_service

По умолчанию используется `ml.service_inference:analyze` и `FORTE_MODEL_DIR=models`.
В папке должны быть **все три** файла: `forte_det.pt` (объектный детектор),
`forte_door.pt` (дверь), `forte_safe.pt` (сейф). Они включены в репозиторий и
монтируются Docker как read-only. Headless Ultralytics требуется версии >=8.4: после CPU PyTorch установите
`pip install -r ml/requirements-service.txt`.

Исходный алгоритм находится в `ml/forte_service.py`. Импорт Ultralytics перенесён
в конструктор для работы контрактных тестов без ML; оформление приведено к lint проекта.
Правила, сглаживание, выбор рабочей зоны, confidence и предобработка сохранены.
Детектор получает BGR-кадры OpenCV, классификатор двери — весь кадр, классификатор
сейфа — расширенный crop детекции `safe`. Размеры входов 864 / 320 / 224,
частота 2 FPS, порог детектора 0.25. Пороговые значения сигналов берутся из скрипта.
Названия классов читаются из новых весов; старые числовые ID не используются.

| Событие автора | ID API |
| --- | --- |
| cash_left | ML02 |
| bag_left | ML03 |
| laptop_unlocked | ML04 |
| door_open | ML05 |
| safe_open | ML06 |
| previous_cash | ML07 |

Скрипт возвращает первое событие каждого типа, точечный таймкод и кадры.
Адаптер сохраняет тип, описание и таймкоды; JPEG для стандартного API извлекает
бэкенд по исходным временам. Границы эпизода и confidence не выдумываются.
Нормативные ссылки остаются непроверенными ссылками автора, не смешиваются с R01–R07.
Пустое декодирование (`status=failed`) считается ошибкой, а не чистым видео.

`FORTE_ML_DEVICE` и `FORTE_ML_THREADS` поддерживаются. Старые `FORTE_MODEL_PATH`,
`FORTE_ML_FPS`, `FORTE_ML_CONF`, `FORTE_ML_IMGSZ` относятся только к старому адаптеру.
Прогресс обновляется после обработки кадра всеми моделями. Для изоляции и тайм-аута
модели загружаются один раз на задание, в отдельном процессе; скрипт автора хранит
семплированные кадры до подготовки доказательств, поэтому длинные видео требуют больше RAM.
После обновления `.env`: `docker compose up --build -d --force-recreate --wait`.

Отдельный запуск: `python -m ml.forte_service models /path/to/video.mov --out result.json`.

## Предыдущая модель команды (для сравнения)

`ml/inference.py` уже реализован для присланного `analyze_video.py` и YOLO11.
Весовой файл: `models/v0m_early.pt`, SHA-256:
`d4179f8b69e6b1af4a6019fcf8d0b09cb062f0d25e38a0cd0947f874c26bd1ca`.
Он входит в репозиторий; Docker получает его через read-only mount `models/`.

Установка CPU-библиотек: сначала `pip install -r ml/requirements-cpu.txt`,
затем `pip install -r ml/requirements.txt`. Используется headless-вариант Ultralytics:
[официальная инструкция](https://docs.ultralytics.com/quickstart/).

Настройки: `FORTE_MODEL_PATH`, `FORTE_ML_FPS=3`, `FORTE_ML_CONF=0.35`,
`FORTE_ML_IMGSZ=864`, `FORTE_ML_DEVICE=cpu`, `FORTE_ML_THREADS=4`.
Для CUDA установите совместимую GPU-сборку PyTorch отдельно; CPU-сборка из
`requirements-cpu.txt` предназначена для работы без GPU.

Скрипт адаптирован без изменения двух эвристик: кадры декодируются последовательно,
в памяти остаются только детекции и времена; таймкоды нормализуются от первого кадра.
Пустое декодирование считается ошибкой. Формат исходного результата (`verdict`,
`violations`, `kind`, `end_sec`) преобразуется в контракт бэкенда. Диапазоны событий
сохраняются, JPEG на начале и середине эпизода формирует бэкенд.

ML02: наличные и отсутствие человека в рабочей зоне минимум 2 с.
ML01: человек вне рабочей зоны и отсутствие человека внутри неё минимум 3 с.
Роли людей не распознаются; открытый сейф/дверь остаются контекстными сигналами.
Уверенность эпизода автором не вычисляется, поэтому `confidence` отсутствует в API
для этого адаптера. Порог `FORTE_ML_CONF` относится к объектным детекциям.
Нормативные пункты 20/22 из скрипта не подтверждены и не выдаются за проверенные.

Проверено локально 18.10.2026: PyTorch `2.9.1+cpu`, torchvision `0.24.1+cpu`,
Ultralytics `8.4.181` (совпадает с версией в чекпойнте), PyAV `18.1.0`.
На четырёх MOV API завершил настоящий анализ. Три коротких ролика длительностью
11,6–14,7 с обработаны за 22,3–25,3 с; ролик 142,5 с — за 204,6 с при 3 FPS,
imgsz 864 и 4 CPU threads. Это замеры данного компьютера, не гарантия для любого видео.
На всех четырёх роликах модель вернула `no_violation`; размеченных эталонных вердиктов
для оценки точности не было. На одном ролике результаты детектора сверены с
исходным скриптом: вердикт, эпизоды, сигналы и рабочая зона совпали.

Расширенная проверка 20 роликов нашла реальный положительный пример: `Х-46.mov`,
ML02 на 1,33–5,00 с, 8,00–11,33 с и 13,67–17,33 с. Все три эпизода подтверждены
исходным скриптом и сохранены Docker API вместе с шестью JPEG-доказательствами.
Подробности и границы проверки: [MODEL_AUDIT.md](MODEL_AUDIT.md).

Положительный путь ML01/ML02 проверяется отдельной интеграционной фикстурой:
API возвращает оба правила, диапазоны и декодируемые JPEG. Это тест интеграции,
а не подтверждение качества распознавания.

Без HTTP можно получить исходный JSON:

```bash
python -m ml.analyze_video --model models/v0m_early.pt /path/to/video.mov --out result.json
```

## Контракт для замены адаптера

Бэкенд уже принимает видео и возвращает формат жюри. ML-разработчику достаточно
реализовать одну функцию; HTTP-сервер на стороне ML не требуется.

```python
# ml/inference.py
def analyze(video_path: str) -> dict:
    # video_path — абсолютный путь к уже сохранённому локальному видео.
    # Здесь настоящий анализ локальной моделью.
    return {
        "detections": [
            {
                "type": "Пересчёт после ухода клиента",
                "timecode_sec": 12.4,
                "description": "Клиент покидает зону, после чего кассир начинает пересчёт.",
                "rule_id": "R02",
                "confidence": 0.85,
                "evidence_timestamps": [10.0, 12.4],
                "alternative_explanation": "Возможно, это повторный внутренний пересчёт.",
                "missing_data": ["Подтверждение типа операции"],
            }
        ],
        "limitations": [],
    }
```

Это пример формата, не готовый детектор. Не копируйте фиксированный результат в
рабочую функцию. Заготовка с `NotImplementedError`: `ml/adapter_example.py`.

| Поле | Требование |
| --- | --- |
| `detections` | Обязательный список, до 100 эпизодов |
| `type` | Понятное название наблюдаемого возможного нарушения, 1–200 символов |
| `timecode_sec` | Конечное число, `0 <= t < длительность`, секунды от начала файла |
| `start_sec`, `end_sec` | Необязательная пара границ: `0 <= start_sec <= timecode_sec < end_sec <= длительность`. Если модель знает диапазон события, передавайте оба поля. |
| `description` | Наблюдаемое действие и основание для проверки, 1–3000 символов |
| `rule_id` | ID из `GET /api/v1/rules` / `backend/app/rules.json` |
| `confidence` | Необязательное число от 0 до 1; уверенность модели, не вероятность юридического нарушения. Если модель не вычисляет оценку, пропустите поле или передайте `None`. |
| `evidence_timestamps` | Необязательный список из 0–3 таймкодов; по умолчанию `[timecode_sec]` |
| `alternative_explanation` | Необязательное альтернативное объяснение |
| `missing_data` | Необязательный список недостающих данных |
| `limitations` | Необязательный список ограничений анализа всего видео |

Отрицательный результат успешного анализа:

```python
return {"detections": [], "limitations": []}
```

Если веса отсутствуют, видео не удалось проанализировать или модель упала,
**поднимите исключение**. Не возвращайте пустой список как замену ошибки — иначе
жюри получит неверный `no_violation`. Нечитаемый фрагмент нужно отразить в limitations;
если надёжный анализ целиком невозможен, завершить исключением. Третьего вердикта
в API кейса нет.

JPEG и base64 формирует бэкенд; их возвращать не нужно. Неизвестные ID правил,
таймкоды вне видео, NaN, бесконечность и лишние поля приводят к `invalid_model_output`.
Дублирование эпизодов и порог уверенности — ответственность ML-адаптера: бэкенд
не отбрасывает распознанные события по произвольному порогу.

Запуск:

```dotenv
FORTE_ANALYZER_MODE=plugin
FORTE_ML_CALLABLE=ml.service_inference:analyze
```

Можно указать другой импортируемый модуль и имя функции. Функция синхронная, принимает
одну строку-путь и возвращает обычный `dict`, совместимый с описанной схемой.
Опционально функция может объявить keyword-параметры `on_progress=None` и
`duration=None`: бэкенд передаст callback и длительность видео в секундах.
Вызывайте `on_progress(fraction)` с долей обработанного видео от 0 до 1.
Адаптер YOLO сообщает её после инференса очередного кадра по его таймкоду;
бэкенд переводит её в диапазон 20–80% общего задания. До этого выполняются
проверка файла и загрузка модели, после — подготовка кадров-доказательств и
сохранение результата. 100% выставляется только при успешном завершении.
Старые функции без этих параметров продолжают работать, но дают только этапный прогресс.
Запуск сервера — из корня репозитория. Дополнительные зависимости ML установите
в окружение сервера и зафиксируйте в отдельном файле зависимостей.

Каждое задание запускается в новом процессе: веса сейчас загружаются на каждое
видео. Это обеспечивает принудительный тайм-аут и изоляцию. Если загрузка весов
дорогая, обсудите с backend-разработчиком постоянный ML-процесс; контракт результата
можно сохранить. Цель — обработка в пределах 270 секунд вместе с очередью, желательно
существенно быстрее. Профилируйте на компьютере демо.

Вызовы облачных AI запрещены кейсом. Загружайте веса заранее, задавайте
`local_files_only=True` там, где библиотека это поддерживает. Не анализируйте звук,
не распознавайте и не идентифицируйте лица. Не публикуйте тестовые данные.
